# claude-code-wrapper memory

Lessons that outlive a session. Newest first.

- 2026-10-31 (agents-ui-improvements C6) peer messages carry a lane, `regular` by default: `MessageBody.lane`, `send_message` `lane`, `InboxItem.lane`; the inbox delivers through `SessionRouter.deliver`. On a ready session the head goes first whatever its lane (FIFO as before); while busy, the first non-idle message goes when `check_queueable` passes, so `idle` items and notices keep waiting without blocking it. A typed peer message's `notify_when_idle` outcome follows `prompt_delivered` to the turn that read it (`message_delivered`), so the idle notice is not sent at the end of a turn that never saw it. The old peer inbox tests pin `lane: "idle"` (their `msg()` helper): they test delivery as a new turn, which the default no longer is.
- 2026-10-31 (agents-ui-improvements C5) a typed message is delivered by its transcript marker, and a late one is adopted as a new turn: `SessionRouter._message_delivered` handles a main-chain `UserPrompt.message_id` (user line or `queued_command` attachment; real attachments wrap the paste in `<pasted_content>`, the marker still matches). Busy: the model took it in the running turn (`prompt_delivered`, `new_turn: false`), no new Stop is expected. Ready: claude sent it after the turn's Stop (claude sends still-queued messages when a turn ends or is interrupted), so `Session.deliver_message` creates a running record from the message and `_last_marker` names it, because that Stop carries no marker of its own and would otherwise be read as a background completion (`origin: agent`). The Stop relay flushes the transcript first, so the marker is always read before its Stop. The fake claude models this behind the scenario key `queue_input` (opt-in, so the "busy input is dropped" tests keep their meaning).
- 2026-10-31 (agents-ui-improvements C4) dialog detection for the lanes is screen footers cleared by hooks: `Session.dialog_open` is a `sessions.commands.dialog_patterns` footer seen on screen after the last relayed claude hook (`note_hook`, from `handle_claude_hook`) and the last ESC; the last typed text's own footers are ignored (its echo). Why footers and hooks, not transcript lines: a permission prompt fires PreToolUse before it paints and nothing after it until answered, while the tailer can read a line written before the prompt after it paints, which would clear it too early. Why not a PermissionRequest/Notification relay: it would add claude hook events (settings.json) for a signal the screen already gives; noted, not doing now. Known gaps: a parallel subagent's hook clears a main-agent prompt early, and assistant text quoting a footer looks like a dialog until the next hook (fails safe: 409, the caller retries or uses the idle lane).
- 2026-10-31 (agents-ui-improvements C3) priority = veto, spaced interrupt, then a new turn: on a busy session `SessionRouter._priority` fires onTurn first (a vetoed message must not cost the running turn), then `interrupt(spaced=True)` (the same ESC, settle wait and second-ESC escalation as `POST /interrupt`, with every ESC through `send_escape` so it keeps `ESC_SPACING_SECONDS`), then `submit_turn` with the already vetted turn id and outcome. Why not Ctrl+X Ctrl+S (`chat:sendNow`, RD 2.4): it backgrounds running shell and subagent work instead of stopping it and needs claude 2.1.275+; ESC is the documented interrupt and reuses the tested path. Only `spaced` is new on the interrupt path; a plain interrupt is unchanged.
- 2026-10-31 (agents-ui-improvements C2) regular lane types into the running turn, with a message marker and no turn marker: `POST /turns` defaults to `lane: "regular"`; on a busy session `Session.queue_prompt` pastes `text\n\n<!-- ccw message: <id> -->` then one CR (no ESC), the running record keeps the slot and its single Stop. Why no turn marker: the paste may be absorbed mid-turn (then `_last_marker` must stay on the running turn) or run after the Stop as claude's own next turn, and the message marker identifies it either way. A slash command run, its command phase or a held (crash) turn refuses it `409 busy`: typing then reaches a command line or a dialog, not the model. Regular and priority answer `409 booting|dead` when claude is not live (plan item 4: the wrapper rejects them only then), idle keeps `503`. onTurn still fires for a queued message (`lane`, `queued: true`) so a veto hook cannot be bypassed by picking a lane. Existing tests that meant "a new turn or 409" now send `lane: "idle"` (test_api_turns error mapping, test_peers_e2e, integration_peers); the default changed under them.
- 2026-10-29 (slash-commands-from-chat) slash rule uses JS whitespace and skips Cc/Cf characters (F1, wrapper 0.4.1): `slash_command` (session.py) splits and strips with exactly JavaScript `\s` (U+0009-000D, 0020, 00A0, 1680, 2000-200A, 2028, 2029, 202F, 205F, 3000, FEFF), an explicit frozenset, never `isspace`, `strip()`, `lstrip()` or regex `\s` (Python adds U+001C-001F and U+0085 and lacks U+FEFF; the run-marker regex spells its class out too). Leading whitespace and every other Cc or Cf character is skipped, and Cc/Cf characters are dropped from the name, so U+001C-001F skip when leading but no longer split it; args are stripped of whitespace only. `Session.probe` runs the same check first and raises `TurnRejected("slash_command")` (422 on `POST .../probe`, counted `rejected`). Why: claude 2.1.304 does `trim()` then startsWith "/" (`Kb`), cuts the name at `search(/\s/)` and `trim`s the args (`hIe`), and looks the name up exactly; our old space/tab/newline split classed `/exit<U+00A0>x` and `<U+FEFF>/login` as prose, `pty_proc.paste_bytes` deletes ESC so `/ex<ESC>it` and `<ESC>/exit` reached claude as `/exit`, and the probe pasted client text with no guard. Calling more text a command is the safe direction (D2). The same case table lives in agents-orchestrator `tests/test_slash.py`. Evidence: `/workdir/workdir/.scratchpad/slash-fix-design.md` (binary offsets 254536412, 267231000, 243756307).

- 2026-10-29, command completion is class-agnostic (slash-commands-from-chat D6): after the runner types a line, the first `command_invoked` of any name then the next `command_output` completes it, and a `command_unknown` fails it `unknown_command` at once without an ESC. Why: claude echoes the resolved alias (`/cost` echoes `/usage`), and writes the echo of `/context` and of every dialog command as a `system`/`local_command` line, so matching the typed name, or reading only user echoes, timed those commands out. An unknown name leaves claude idle at its prompt, so an ESC there would only reach the next input. The transcript parser reads a `system`/`local_command` body starting `<command-name>` as `CommandInvoked` and a `system`/`informational` "Unknown command: /x" (with or without ". Did you mean /y?") as `CommandUnknown`; other informational lines, "Args from unknown skill" included, yield nothing.

- 2026-10-28, `queued_command` attachments are prompts (fix for queued messages never loading on tatara): `parse_line` reads a transcript line `type: "attachment"` whose attachment is a `queued_command` as the prompt text it carries, through the same classification as a user line (turn marker, probe, interrupt, command echo). Why: when a background task notification wakes Claude while the wrapper reports ready, the wrapper pastes the next turn and Claude absorbs it mid-turn; the transcript records that prompt only as this attachment line. The parser used to drop attachment lines, so `Router._last_marker` never moved to the running turn and `Session.stop_target` treated every later Stop as stale: the wrapper stayed busy for good and the orchestrator never delivered queued messages. Attachments of any other type still yield nothing. Not changed: the wrapper still accepts a turn while a background wake is running.
- 2026-10-28, resume_on_start after a graceful shutdown (deploy-safe-agent-sessions D5, fix round): `load_persisted` also resumes a session persisted `stopped` whose `TurnStore.current` carries `interrupted: "shutdown"` (`SessionManager._shutdown_left_turn`), not only the sessions a killed process left live. Why: a pod restart is a graceful shutdown, so it leaves every session `stopped`. If only live sessions were resumed, the D5 continuation would run only after a crash, never on the deploy it exists for. A user stop or delete ends the turn `failed` `session_stopped` and clears the marker, so those sessions are never picked up. That is also why a `DELETE` of an already-stopped session (`_end_left_turn`) fails a turn an earlier process left `running`: without it, a session deleted between the shutdown and the next start would come back on `resume_on_start` and its turn would be continued against the user's delete.
- 2026-10-28, service shutdown keeps the turn (D5): `shutdown` stops sessions with cause `shutdown`, which leaves the running turn `running` in `turns.jsonl` with the marker `interrupted: "shutdown"` and emits no `turn_failed`, no `onTurnComplete` and no callback. Every other stop ends the turn `failed` `session_stopped`. On resume (the API or `resume_on_start`), the fresh Session adopts `TurnStore.current`, clears the marker, and once claude is ready continues the same `turn_id` with `sessions.restart_continue_prompt` (`turn_resumed`, cause `resume`; an in-process crash relaunch keeps cause `restart`). Without the prompt, or when claude never boots, the turn ends `failed` `service_shutdown`. A turn a killed process left `running` without the marker is adopted the same way. Why: the orchestrator's turn row and message then complete normally across a deploy. Rejected: failing the turn at shutdown and starting a new turn on resume, because the orchestrator would record a failure and the message would never complete.
- 2026-10-28, turn_max_seconds spans the resume (D5): the timeout keeps counting from the turn's original submit (`started_at`), not from the resume. A turn already over the limit when it is adopted ends `timeout` without a paste. Why: a turn that keeps getting cut off by restarts must still be bounded. Restarting the clock on every resume would let a turn outlive the limit indefinitely.
- 2026-10-28, an in-flight interrupt wins over the shutdown (D5): when the shutdown arrives while a turn is already being interrupted, the turn ends as the interrupt would have ended it (`interrupted`) instead of being marked for a resume. Why: the user already asked for that turn to stop, so continuing it after the restart would undo their request.
