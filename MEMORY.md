# claude-code-wrapper memory

Lessons that outlive a session. Newest first.

- 2026-10-28, resume_on_start after a graceful shutdown (deploy-safe-agent-sessions D5, fix round): `load_persisted` also resumes a session persisted `stopped` whose `TurnStore.current` carries `interrupted: "shutdown"` (`SessionManager._shutdown_left_turn`), not only the sessions a killed process left live. Why: a pod restart is a graceful shutdown, so it leaves every session `stopped`. If only live sessions were resumed, the D5 continuation would run only after a crash, never on the deploy it exists for. A user stop or delete ends the turn `failed` `session_stopped` and clears the marker, so those sessions are never picked up. That is also why a `DELETE` of an already-stopped session (`_end_left_turn`) fails a turn an earlier process left `running`: without it, a session deleted between the shutdown and the next start would come back on `resume_on_start` and its turn would be continued against the user's delete.
- 2026-10-28, service shutdown keeps the turn (D5): `shutdown` stops sessions with cause `shutdown`, which leaves the running turn `running` in `turns.jsonl` with the marker `interrupted: "shutdown"` and emits no `turn_failed`, no `onTurnComplete` and no callback. Every other stop ends the turn `failed` `session_stopped`. On resume (the API or `resume_on_start`), the fresh Session adopts `TurnStore.current`, clears the marker, and once claude is ready continues the same `turn_id` with `sessions.restart_continue_prompt` (`turn_resumed`, cause `resume`; an in-process crash relaunch keeps cause `restart`). Without the prompt, or when claude never boots, the turn ends `failed` `service_shutdown`. A turn a killed process left `running` without the marker is adopted the same way. Why: the orchestrator's turn row and message then complete normally across a deploy. Rejected: failing the turn at shutdown and starting a new turn on resume, because the orchestrator would record a failure and the message would never complete.
- 2026-10-28, turn_max_seconds spans the resume (D5): the timeout keeps counting from the turn's original submit (`started_at`), not from the resume. A turn already over the limit when it is adopted ends `timeout` without a paste. Why: a turn that keeps getting cut off by restarts must still be bounded. Restarting the clock on every resume would let a turn outlive the limit indefinitely.
- 2026-10-28, an in-flight interrupt wins over the shutdown (D5): when the shutdown arrives while a turn is already being interrupted, the turn ends as the interrupt would have ended it (`interrupted`) instead of being marked for a resume. Why: the user already asked for that turn to stop, so continuing it after the restart would undo their request.
